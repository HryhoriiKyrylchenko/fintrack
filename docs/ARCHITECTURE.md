# FinTrack: Personal Finance Tracker. Architecture and Requirements (v2)

Status: design baseline, 15 Nov 2026. Supersedes all earlier drafts.
Place this file at `docs/ARCHITECTURE.md`. It is the source of truth for the design.
Priority tags: **[P1]** build first, **[P2]** next, **[Later]** deferred but the model leaves room.

## 1. Goals and principles

- A personal finance platform, budget planning first: money is split into buckets, with contribution plans, self-loans, and investment buckets with richer mechanics (crypto first, then stocks/ETFs).
- Manual entry is the primary input. Read-only imports from exchanges, wallets and brokers come later; the groundwork is built in from the start.
- Fully serverless and ready to deploy to the cloud, but it must run completely on a local machine for one user. The cloud may never be used; nothing may depend on it.
- Cost tends to zero: free tiers only, pay-per-use, no always-on compute.
- Correctness first. Financial history is never lost, entries are never edited, and no balance goes negative.
- Build in phases. Fewer features, done well. Models leave room to grow, but no dead code.
- Open source from the start: public GitHub repository under **AGPL-3.0**. Possible future: several users (SaaS). Each user is an individual account; there are no family groups.

## 2. Architecture

### 2.1 Shape

- **Front end**: Blazor WebAssembly, hosted as a static site. Installable as a PWA later (this replaces a separate mobile app).
- **Back end**: Azure Functions, .NET 10 (LTS), isolated worker model. Each function is one small endpoint or job: HTTP-triggered (`AddDeposit`, `PausePlan`, `GetBalances`), timer-triggered (price refresh, outbox sweep, valuation snapshot). A function only parses input, calls one mediator handler and maps the `Result` to a response. No business logic in functions.
- **Code organization**: bounded contexts as class libraries: `Budget`, `Investments`, `Integrations`, plus `Shared` (kernel). Each context has `Domain`, `Application` (CQRS through the source-generated `Mediator` library, Result pattern), `Infrastructure` and a small `Contracts` project. A context may reference only another context's `Contracts`, never its Domain or Infrastructure. `Shared` is two projects: `FinTrack.Shared.Kernel` (plain types and abstractions; its only package is FluentResults, so every Domain project can reference it) and `FinTrack.Shared.Infrastructure` (the MongoDB adapter, the outbox dispatcher and the mediator pipeline behaviours; never referenced by Domain or Application). Context projects are created in the phase that first needs them.
- **Deployment units**: **one Function App (`Api`) that hosts the functions of all contexts**, grouped by folder. This is serverless: it scales to zero and is billed per execution. One app means one deployment, one cold start, and atomic operations inside one process. Because contexts are isolated by references, splitting into one Function App per context later is a move of folders, not a redesign. Do not build a long-running ASP.NET host.

### 2.2 Storage: MongoDB (decided)

- One database engine everywhere: **MongoDB** with the official .NET driver. Local: MongoDB Community as a single-node replica set. Cloud: **MongoDB Atlas** (free cluster to start).
- Why MongoDB and not Cosmos DB (final): the app must be able to live on a local machine forever. MongoDB is a real database that can be installed and self-hosted; Cosmos DB cannot. Locally Cosmos exists only as an emulator, which is a development tool (the current one is a Docker-only preview with a subset of features) and not a place to keep real financial data for years. MongoDB also gives the same engine and the same code locally and in the cloud, real multi-document transactions and no lock-in. Cosmos DB for MongoDB limits transactions to a single unsharded collection, which does not fit. If the app is deployed to Azure, the Atlas cluster can be created in an Azure region next to the functions.
- Transactions require a replica set, so the local `mongod` runs with `--replSet` (one node is enough).
- Supported server versions: **8.0 or later**. 8.0 matches the Atlas free cluster and is the version CI tests against; a local server may be newer. Setup: `docs/LOCAL-SETUP.md`.
- Each context owns its collections. No cross-context queries or joins. Aggregates are stored as documents.
- Every document carries `Id` (UUIDv7: generated by the client for everything a user creates, which is also how a repeated command is recognised (2.7); generated by the server for documents the system creates itself, such as a `LedgerHead` or the `Unallocated` bucket), `OwnerId` and `SchemaVersion`. Beyond that there are two shapes:
  - **Mutable documents** (aggregates, settings, `LedgerHead`): also `Version` (optimistic concurrency), `CreatedAt`, `UpdatedAt`, and a soft-delete flag where deletion is allowed at all.
  - **Append-only documents** (journal entries, outbox messages, processed-event records): also `RecordedAt`. They are never updated, so they have no `Version` and no `UpdatedAt`. Delivery bookkeeping on an outbox message (attempts, dispatched time) is the only field group that changes after insert.
- Storage format (fixed in phase 0; a later change needs an upcaster): element names in camelCase, `Guid` and strongly typed IDs as standard UUID (binary subtype 4), `decimal` as `Decimal128`, enums as their names, business dates (`DateOnly`) as ISO strings (`yyyy-MM-dd`), business months (`YearMonth`, from phase 1b) as `yyyy-MM` strings, instants (`DateTimeOffset`) as BSON dates in UTC with whole milliseconds, `Currency` as its code, `Money` as `{ amount, currency }`. Reading is strict: an unknown element, a decimal stored as a double or integer, an enum stored as a number or an unknown name, or an unregistered currency makes the read fail. Writing an instant with an offset or a sub-millisecond part fails; `IClock` returns UTC in whole milliseconds, so a value read back equals the value written. The format lives in `FinTrack.Shared.Infrastructure/Mongo/MongoSerialization`. Each context maps its domain types explicitly (for Budget, `BudgetMongoMapping`): every stored property by hand with an explicit element name, so renaming a C# property never changes what is stored; every element required, except a field that is optional by design, which is not written when empty and reads as empty when missing (so adding one later needs no upcaster); the type's private constructor restores a stored document. Subtypes stored in one collection (the journal entry types) carry an element `type` whose value is a stable name declared in the context's mapping (the type name of 4.2, for example `Deposit`), never the CLR class name; a guard test requires one for every subtype.
- Collection names are prefixed by context. Per context, besides its own collections: `<ctx>_ledger_heads`, `<ctx>_outbox`, `<ctx>_processed_events` (for Budget: `budget_ledger_heads`, `budget_outbox`, `budget_processed_events`). Budget's own collections: `budget_journal` (index `{ ownerId, occurredOn, recordedAt, _id }` for the replay order, 4.2), `budget_buckets`, `budget_settings`.
- **Reference data**: public data that is the same for every owner (FX rates now, asset prices in phase 3) lives in collections prefixed `ref_` (`ref_fx_rates`). It has no `OwnerId` and is read and written only through its own collection type (`ReferenceCollection<T>`); owner data is never stored there. Both directions are enforced: `ReferenceCollection<T>` accepts only `ref_` names and only types that are not owner documents (`IReferenceDocument`, which also requires an explicit mapping), and the owner-scoped collections refuse `ref_` names. Reference documents are written by the system with a single-document upsert by their unique key, outside any ledger commit. This is the second documented exception to owner scoping (2.3).
- Free tier limits change. Verify before deployment. At the time of writing the Atlas free cluster had 512 MB storage and about 100 operations per second.

### 2.3 Consistency

- **The journal is the source of truth.** It is append-only.
- **State is derived by replay.** Balances, plan status and positions are computed from the journal on each request. For one user the journal is small, so this is fast and removes a whole class of consistency bugs.
- **Stored projections are deferred, not dropped.** They are added as an optimization when measurements show replay is too slow (many users, long history). They will then be a rebuildable cache, and a test will assert projection == replay. Code that reads state goes through one place per context (a state builder), so adding a cache later does not touch handlers.
- **Write path**: read the owner's `LedgerHead.Version` → **then** load the owner's journal → build state → validate invariants → in **one MongoDB transaction**: insert journal entries, insert or replace the context's changed mutable documents (for example a bucket), increase the owner's `LedgerHead.Version` (a single small document per owner and context, checked for the version read first), insert outbox events, and for an event handler record the handled event. A version conflict means another write happened in between: reload and retry. The version is read before the journal so that a write landing in between makes the commit fail instead of passing on stale data. It is read again after the documents: the documents are separate reads, so a commit could land between them (a journal entry for a bucket the bucket list did not have yet); an unchanged version proves one consistent state, a changed one means reading again (at most 3 times, then `concurrency.conflict`). Handlers have no side effects before the commit, because a retry runs them again. The contract is `ILedger` in the shared kernel.
- **Domain types are the stored documents.** Journal entries and aggregates implement the kernel's document interfaces and are mapped to MongoDB in Infrastructure; Domain has no database attributes and there is no second set of persistence classes.
- **Events between contexts**: transactional outbox. Events are written in the same transaction as the data, dispatched in-process right after commit, and a timer function re-dispatches anything left undelivered. Handlers are idempotent (they record processed event IDs). No queue is needed while there is one Function App. A queue (Azure Storage Queue) is introduced only if apps are split or for long-running imports.
- **Two exceptions to owner scoping.** (1) The outbox sweep: the timer function must find undelivered messages of all owners, so its query for pending outbox messages is not filtered by `OwnerId`; each message is then handled under that message's own `OwnerId`. (2) Reference data (2.2): FX rates and later prices are public and have no owner, so `ref_` collections are not filtered by `OwnerId`; they never hold owner data. No other query or write may skip the owner filter.
- Stored events are identified by a stable event name declared on the event type, never by the CLR type name, because stored events outlive refactorings.
- **Schema evolution**: `SchemaVersion` on every document; old versions are upgraded on read (upcasters). The journal lives forever, its format will change.

### 2.4 Local run (no Docker required)

- Prerequisites: .NET SDK, Azure Functions Core Tools, MongoDB Community (local service, single-node replica set), Azurite (storage emulator, needed by timer triggers).
- One command or script starts API and Web. The code path is identical to the cloud. Works offline except for price, FX and import calls.
- An optional Docker Compose file may be provided for MongoDB and Azurite as a convenience, never as a requirement.
- Local mode: one default user, no login. Data lives in the local MongoDB data directory, outside the repository. Automatic backup = scheduled `mongodump` to a user-chosen folder, plus JSON/CSV export from the app.

### 2.5 Cloud [Later]

- Azure Static Web Apps (front end), Azure Functions on the **Flex Consumption** plan (the older Linux Consumption plan does not receive .NET 10), MongoDB Atlas, Key Vault for secrets, Application Insights for logs. Infrastructure as Bicep templates.
- Authentication through an external OIDC provider. The app never stores passwords. `OwnerId` comes from the token. The code depends only on standard OIDC and JWT validation, so the provider is replaceable by configuration. Default choice: **Microsoft Entra External ID** (same Azure account and bill, has a free tier). Alternative: Auth0 (free plan, simpler setup, not tied to Azure). Confirm free-tier limits before going live.
- Mandatory before going live: an Azure budget alert, because usage above free grants is billed.
- Agents and other long-running work (section 12) run asynchronously on a queue-triggered function; this is the point where a queue is introduced.
- SaaS readiness: per-user data isolation by `OwnerId` in every query (enforced in the repository base class), data export and account deletion, sign-in audit log.

### 2.6 Read contracts (built from phase 1)

- Every context exposes **read-only summary queries with stable, versioned DTOs** in its `Contracts` project: bucket balances, plan status and dues, loans, portfolio totals, sections, positions with PnL, targets and their status, value history. The UI uses them now. Later the same queries become the tools of AI agents (section 12) and the input for reports. Keep them free of UI concerns and document each field.
- A context's `Contracts` project holds its read queries as mediator messages (`IQuery<Result<T>>`), so that another context, and later an agent, can send them; their DTOs in a versioned namespace (`V1`); and the request bodies of the context's HTTP endpoints. Commands and all handlers stay in `Application`. `Contracts` may therefore reference `Mediator.Abstractions` and `FluentResults`, and nothing else besides the kernel. Budget's first queries (phase 1a): overview, buckets, journal, owner settings; phase 1b adds plans, loans and an allocation preview.
- **How a version grows:** within `V1`, changes are additive only: new response properties, new enum members, new request properties with a default (strict reading makes a property optional only through its default), new queries. Renaming or removing a property, changing its meaning or making it required is a `V2`. Strict reading means an older client fails on a newer Api; that is acceptable while the Api and the Web app ship together, and pinned JSON tests make every change deliberate. Other contexts and, in phase 7, agent tools send the query types in-process, where an added property breaks nothing. The first consumer that does not ship with the Api (a split deployment, an external client) freezes `V1`; later changes go to `V2`.

### 2.7 Engineering conventions

- **API errors**: every failure is returned as RFC 7807 `ProblemDetails` built from the `Result`. Each business error has a **stable error code** (for example `bucket.insufficient_funds`) plus parameters. The back end never returns user-facing sentences as the contract; the UI turns codes into text. Status by error kind: Validation 400, NotFound 404, Conflict 409, BusinessRule 422, Unavailable 503; an unexpected failure is 500 with code `server.error` and no details. Body: `type` (`urn:fintrack:error:<code>`), `title` (the code), `status`, `code` and `params` of the first error, and `errors` (every error as `{ code, params }`).
- **JSON contract (HTTP)**: camelCase, enums as names, business dates as `yyyy-MM-dd`, instants as ISO 8601 in UTC, and **amounts as JSON strings** (`"amount": "1234.56"`) next to their currency code: a JSON number is read as a binary double by JavaScript and most tools and cannot hold 18 decimal places. One set of serializer options in the kernel (`FinTrackJson`) serves the Api and the Web app. Exact shapes:
  - every `decimal` (amounts, rates) is a string with its exact scale: `"1.10"` stays `"1.10"`; `Currency` is its code (`"PLN"`); `Money` is `{ "amount": "1.10", "currency": "PLN" }`, and its amount always has exactly its currency's decimal places (section 3): an amount sent as `"50"` for PLN is accepted and comes back as `"50.00"`, and zero is `"0.00"`, so every amount has one spelling;
  - strongly typed IDs are the GUID string (`"0190a1b2-c3d4-7e5f-8a6b-7c8d9e0f1a2b"`); dates `"2026-01-15"`; months `"2026-01"`; instants `"2026-01-15T09:30:00.123Z"` (always `Z`, the fraction only as long as needed); enums their exact member name (`"Deposit"`).
  - Reading is strict, like the storage format: a decimal sent as a number, with an exponent, `+`, leading zeros or more places than a `decimal` holds; an unregistered currency or an amount with more decimals than its currency; an enum as a number or in another case; an instant without `Z`; an unknown, repeated or missing property and `null` for a non-nullable value are all rejected, never converted. A property is optional only when its constructor parameter has a default.
  - A route or query value the Api cannot read (a malformed `{id}`, a flag other than `true` or `false`) is a 400 `validation.failed` with `field` = the parameter and `rule` = `RouteFormat` or `QueryFormat`; route constraints are not used, because a mismatch would be a bare 404.
  - A request body the Api cannot read is a client error: 400 with one `validation.failed` error, `rule` = `JsonFormat` and, when the failure is at a property, `field` = its camelCase path (`price`, `lines[1]`); the value sent is never echoed. The precise codes (`currency.unknown`, `money.too_many_decimals`) come from the kernel's own checks, which the Web app runs on user input before sending.
  - `ProblemDetails` bodies keep their shape (`params` values are JSON numbers, strings and booleans as before; a `decimal` parameter would be a string).
- **Repeated commands (invariant 13)**: a command carries the client-generated ID of what it creates. If that document already exists and equals what the command would write, the command succeeds and writes nothing; if it differs, it fails with `<object>.id_reused` (for example `entry.id_reused`). A concurrent duplicate hits the unique `_id`, is retried as a conflict and then takes the same path. There is no separate record of handled commands.
- **Language**: the UI is English only for now. All user-facing strings live in resource files (`IStringLocalizer`) from the first screen, with no text concatenation and no hard-coded strings in components. Numbers, dates and currency formatting follow the user's locale setting. Translations are added later without touching code.
- **Logging**: structured logging through `ILogger`. Never log amounts, balances, account identifiers, API keys or personal data; log IDs and error codes.
- **CI**: build and all tests run on every push (GitHub Actions). A failing test blocks merging.

### 2.8 Configuration and secrets

- The repository contains code and example configuration only. No financial data and no secrets, ever.
- Local secrets: .NET user secrets or environment variables. Cloud: Key Vault.
- Exchange and broker API keys are read-only keys, stored encrypted. Wallet private keys and seed phrases are never requested or stored.

## 3. Shared kernel

- `Money` = `decimal` amount + `Currency`. Arithmetic across different currencies is a compile-time or runtime error (an exception: it is a programming error, not a business rule failure); conversion is always explicit.
- Precision per currency: each `Currency` carries its own number of decimal places (0 to 18). Most fiat currencies have 2 (PLN, EUR and USD are registered first), some have 0 or 3; crypto quantities use up to 18. A `Money` value never has more decimals than its currency allows; user input with more decimals is rejected, never rounded silently. Its amount always carries exactly the currency's number of decimal places (`50` PLN is `50.00`, zero is `0.00` and has no sign): trailing zeros are added or dropped when a value is created, read or computed, never a digit, so an amount has one spelling in JSON, in storage and in every total. Rounding a single value (for example a conversion): banker's rounding at the currency's precision. A split into parts (by positive weights): each part is cut toward zero at the currency's precision and the remainder (less than one minor unit per part) goes to the first line, so the parts always sum exactly to the original and never have the opposite sign.
- **Multi-currency [P1]**: every bucket has one currency, chosen per bucket (PLN, EUR, USD and so on). The owner has a `ReportingCurrency` setting for totals and reports; it is chosen on first run and can be switched at any time (PLN, EUR, USD), because totals are computed at read time. Crypto portfolios are always valued in USD; stablecoins such as USDT and USDC are assets priced against USD. A movement between different currencies records both amounts as entered by the user (what left the source, fee included, and what arrived) and the fee; the rate is derived from the amounts and stored for display, because a typed rate and two typed amounts cannot be kept exactly consistent with rounding (4.2, `Transfer`). Totals across currencies are computed at read time with rates from `IFxRateProvider` (first implementation: the Frankfurter API, free and without an API key, central-bank reference rates including PLN; daily rates, cached, stored historically) and always show the rate date. Converted totals are never stored as truth. `IFxRateProvider` and `FxRate` are declared in the kernel (every context needs them); the Frankfurter implementation lives in `FinTrack.Shared.Infrastructure`. Rates are reference data (2.2), stored per rate date with EUR as the base; a cross rate goes through EUR. A request uses a rate already fetched today (the UTC day of the most recent fetch: rates have no owner, so no owner's time zone applies; on weekends and before the day's publication the answer carries an earlier rate date and still counts as fetched today); otherwise it asks the provider (at most 5 seconds) for every registered currency against EUR and stores the answer by its rate date; when that fails (offline, time-out, an error status, an answer not exactly of the expected shape) it uses the stored rate with the newest rate date; when none exists, the converted total is left out with the reason `fx.rate_unavailable`. A cross rate is the unrounded quotient of the two EUR rates; rounding happens once, when an amount is converted. The caller's own cancellation is never treated as a failure of the source. Logs name the kind of failure and the rate date, never a rate. A total converts each currency's subtotal once, with banker's rounding.
- **Owner settings [P1]**: reporting currency, time zone (IANA ID) and locale (BCP 47 tag; it drives number, date and money formatting). Budget owns them (`budget_settings`, one document per owner, written through `ILedger`); other contexts read them through `Budget.Contracts`. Until they are saved on first run, the Api answers `settings.not_found` and the UI shows only the setup screen; this includes every command that needs "today" (entries, archiving: the state is built for today, plan 1b B20). `PUT /v1/settings` saves all three at once; saving the stored values again writes nothing. The time zone must be an IANA ID and the locale the name of a predefined culture, each in its exact form (`Europe/Warsaw`, `pl-PL`; not `europe/warsaw`, a Windows ID or `pl-pl`), otherwise `settings.time_zone_unknown` or `settings.locale_unknown` (400). The settings document's ID is generated by the server (one per owner, the request carries none). The Web app loads the settings before its first render and applies the locale as the formatting culture (texts stay English); a locale change restarts the app. Instants are shown in the owner's time zone, not the browser's.
- **Two dates on every entry**: `OccurredOn` (business date, chosen by the user) and `RecordedAt` (system time). Backdated entries are allowed; projections from that date are rebuilt. An entry's `OccurredOn` may not be later than today in the owner's time zone (`entry.date_in_future`), so a balance "now" never contains money that has not arrived.
- Time zone and the "month" of a plan follow the owner's configured time zone.
- `Result` pattern for all handlers (FluentResults-based). No exceptions for business rule failures.
- `IClock` abstraction; no direct `DateTime.Now` in domain or application code.

## 4. Budget context

### 4.1 Buckets [P1]

- One entity, `Bucket`. No presets; the user creates buckets. Kinds: `Savings` and `Investment`. Investment profiles: `Crypto` and `RealValueAssets` (stocks, ETFs). **One investment bucket holds exactly one portfolio.**
- Fields: name, currency, kind, profile, status, system role. `Priority` (numeric, phase 2, 4.7) is added in the phase that uses it; an added optional field needs no upcaster, because a missing element reads as empty. A bucket's limit (4.6) is not a stored field: it changes over time and plans depend on its value in each month, so its history is replayed from dated `LimitChanged` entries (phase 1b).
- A name has 1 to 60 characters, no leading or trailing white space and no control characters (rejected, never trimmed: `validation.failed`), and is unique among the owner's non-archived buckets, compared without regard to case (ordinal, after Unicode normalisation to NFC, the same in every locale) (`bucket.name_taken`). Renaming to the current name changes nothing; a change of case only is a rename; an archived bucket cannot be renamed (`bucket.archived`).
- A bucket is created with a client-generated version 7 UUID (`id.invalid` otherwise). A repeat with the same ID and the same name (exact), currency, kind and profile changes nothing; with other values, including after a rename, it fails with `bucket.id_reused` (409). `profile` is required for an investment bucket and absent for a savings bucket. The bucket list (`GetBuckets`) holds definitions only, oldest first, archived buckets on request; balances belong to the overview.
- Buckets are archived, never deleted, and only when they are the lender of no open loan (`bucket.has_open_loan`), have no active plan (`bucket.has_active_plan`, 4.5) and their `NetContributed` is zero (`bucket.not_empty`), checked in this order. (`Available` alone is not enough: a lender whose money is all lent out has `Available` zero.) An archived bucket accepts no new entries and no reversal of an entry that touches it, and cannot be renamed (`bucket.archived`). Archiving an archived bucket changes nothing. Archiving is always the owner's explicit action, never automatic. From phase 1b an archived bucket can be unarchived (`UnarchiveBucket`): it becomes active again with its whole history, unless an active bucket now has its name (`bucket.name_taken`; rename one first); unarchiving an active bucket changes nothing.
- System bucket **`Unallocated`** (one per currency, created on demand): money that has arrived but is not yet distributed. It cannot be renamed or archived (`bucket.system_bucket`) and is included in all totals. It is created by the command that first needs it, in the same commit as that entry, with a server-generated ID; a unique index on owner, system role and currency is the backstop against a second one. Its display name comes from the UI resources.
- Phase 1a: an investment bucket accepts an opening balance, deposits and transfers; spending from it is rejected (`bucket.spend_not_allowed`, 4.9).

### 4.2 Journal [P1]

Append-only. A mistake is fixed by a reversal entry plus a new entry; the UI may present this as "edit". Every entry has: note, tags, `GroupId` (entries created by one user action), `Source` (`Manual`, `Import:<connector>`, `Agent:<name>`), `ExternalId` (for deduplication), `OccurredOn`, `RecordedAt`.

- Each entry type is its own Domain class; all are stored in `budget_journal` with a stable `type` element equal to the type name in the table (2.2). Entries reference buckets and other entries by typed IDs.
- Besides money movements, the journal holds the **definitions** of plans, pauses, limits and repayment plans (phase 1b): they move no money, carry the day the owner made the change as `OccurredOn` and the months they affect as their own fields, and are replayed with the money entries. A plan's ID is the ID of its `PlanCreated` entry, a pause's the ID of its `PlanPaused` entry, a loan's the ID of its `Borrow` entry; nothing about plans, pauses, limits or loans is stored elsewhere.
- A command that writes several entries (an allocation, a deposit with a limit raise) commits them together. Each entry has its own client-generated ID; all carry the command's client-generated `GroupId`. A repeat must match every entry of the group (otherwise `entry.id_reused`): when any of its entry IDs or its group ID is stored, the command writes nothing only if every entry is stored with the same content and group and the stored group holds exactly these entries; a changed entry, a part of a stored group, a group extended by new entries and new entries under a stored group ID are all `entry.id_reused` (plan 1b step 3). Each entry of a group can be reversed on its own.
- Every amount in an entry is strictly positive (`money.amount_not_positive`); the type gives the direction. A bucket has at most one `OpeningBalance` that is not reversed (`bucket.opening_balance_exists`).
- **Replay order**: (`OccurredOn`, `RecordedAt`, `Id`). Entries of one commit share `RecordedAt`, so `Id` breaks the tie: random within a millisecond, but fixed once stored, so every replay of the same journal gives the same order. The ID is compared by its standard (big-endian) bytes, which is how MongoDB sorts stored UUIDs, so memory and database agree (`ReplayOrder`). Index: `replay_order` `{ ownerId, occurredOn, recordedAt, _id }`.
- **Common fields' rules**: `Note` optional, 1 to 500 characters, line breaks allowed, no other control characters, no surrounding white space; `Tags` at most 10, each 1 to 30 characters without surrounding white space or control characters, distinct without regard to case; `Source` stored as `Manual`, `Import:<name>` or `Agent:<name>` (name: lower-case letters, digits, `_`, `-`). Values are rejected, never corrected.
- **Stored shape** (pinned by a raw-BSON test; a change needs an upcaster); `OpeningBalance` and `Spend` have the same shape with their own `type`: `{ _id, type: "Deposit", ownerId, schemaVersion: 1, recordedAt, occurredOn: "2026-01-15", note?, tags: [...], groupId?, source: "Manual", externalId?, bucketId, amount: { amount: Decimal128, currency } }`. `tags` is always written (possibly empty); `note`, `groupId` and `externalId` only when set. `Transfer`: the common fields, then `fromBucketId`, `toBucketId`, `fromAmount`, `toAmount`, `fee` (only when there is one) and `rate` (Decimal128, derived, banker's rounding to 12 decimal places). `Reversal`: the common fields, then `reversedEntryId`. Phase 1b: `Deposit` and `Transfer` gain the optional `planId`; `Adjustment` has `bucketId`, `amount`, `direction` (`Increase` or `Decrease`); `Borrow` has `lenderBucketId`, `principal`, `toBucketId?` (absent: outside); `Repayment` has `loanId`, `amount`, `fromBucketId?` (absent: outside); `PlanCreated` has `bucketId`, `amount`, `validFrom`, `validTo?`; `PlanAmountChanged` has `planId`, `amount`, `from`; `PlanEndChanged` has `planId`, `validTo?`; `PlanPaused` has `planId`, `from`, `to?`, `mode` (`Shift` or `Skip`); `PlanPauseChanged` has `pauseId`, `from`, `to?`, `mode`; `ShortfallWaived` has `planId`, `amount`; `LimitChanged` has `bucketId`, `limit?` (absent: no limit); `RepaymentPlanChanged` has `loanId`, `amount`, `from`. Months (`validFrom`, `validTo`, `from`, `to`) are `yyyy-MM`. Each shape is pinned by a raw-BSON test when its step lands. The state builder leaves out every reversed entry and every reversal before replaying; a reversal's own date is the day of the correction and moves no money. The state builder (`BudgetState`, Domain) replays entries into balances per bucket; nothing is stored about balances.

| Type | Meaning |
|---|---|
| `OpeningBalance` | Starting amount when the user begins using the app. Entered manually, backdated. Not income. |
| `Deposit` | New money into a bucket. Optionally linked to a plan (`PlanId`, a plan of that bucket), otherwise a one-time extra. |
| `Spend` | Money leaves for good. No debt. Includes spending "by purpose" (the cushion used as a cushion). |
| `Transfer` | Between two different buckets, one entry for both sides: `FromAmount` (source currency, everything that leaves the source, fee included), `ToAmount` (destination currency, what arrives), optional `Fee` (source currency, part of `FromAmount`) and `Rate` = `ToAmount ÷ (FromAmount − Fee)`, derived and stored. The amounts are the truth. Same currency: `ToAmount` = `FromAmount − Fee` exactly. Never income. Optionally linked to a plan of the destination (`PlanId`, phase 1b): money already in `Unallocated` pays a plan by transfer. |
| `Borrow` | Taken from a user's savings bucket (not `Unallocated`) with an obligation to return. Opens a `Loan`. The destination is optional: another bucket of the same currency or outside. |
| `Repayment` | Returns loan principal to the lender, from a bucket of the same currency or from outside. Never counted as income. |
| `Adjustment` | Manual correction with a mandatory comment (the note), `Increase` or `Decrease`. Never income; tracked and shown separately in reports. |
| `PlanCreated`, `PlanAmountChanged`, `PlanEndChanged` | A contribution plan, a new version of its monthly amount from a month, and its end month set, moved or removed (4.5). Move no money. |
| `PlanPaused`, `PlanPauseChanged` | A pause of a plan and a later change of it, including the resume (4.5). Move no money. |
| `ShortfallWaived` | Writes off part of a plan's shortfall, with a mandatory reason (the note). Moves no money; never creates a prepayment. |
| `LimitChanged` | Sets, changes or removes a bucket's limit from its date (4.6). Moves no money. |
| `RepaymentPlanChanged` | A new version of a loan's monthly repayment plan from a month (4.4). Moves no money. |
| `Reversal` | Cancels exactly one earlier entry by reference: the referenced entry then counts as if it never happened, at its original date; the reversal itself moves no money. Any entry except a reversal can be reversed, once; a reversal cannot be reversed (to redo, enter a new entry). Reversing a transfer voids both sides. A reversal that would break 4.3 or invariant 4 at any point, or change a plan's period before the current month (invariant 6), is rejected; so is the reversal of an entry that effective entries still refer to (a borrow with repayments, a plan with changes or contributions, a pause with changes: `entry.has_dependents`). |

### 4.3 Balances of a savings bucket [P1]

- `NetContributed` = opening balance + deposits + transfers in − spends − transfers out; from phase 1b also + borrowed into the bucket + adjustments up − repayments paid from the bucket − adjustments down.
- `OutstandingPrincipal` = borrowed − repaid principal.
- `Available` = `NetContributed` − `OutstandingPrincipal`.
- Example: 1,000,000 contributed, 100,000 borrowed and not yet returned → 900,000 available.
- `Available` is never negative **at any point of the replay order** (4.2), not only today: a new or backdated entry, or a reversal, is accepted only if no savings bucket goes below zero after any entry of the resulting journal (`bucket.insufficient_funds`, with the parameter `date`: the first day it would be below zero). Every command checks it by replaying the journal with its new entry; within one day the order is the recorded time, so a spend entered before that day's deposit is rejected. Reaching exactly zero is allowed.
- **Loans in the balances (phase 1b):** a `Borrow` raises the lender's `OutstandingPrincipal` (its `NetContributed` does not change, so `Available` falls) and the destination's `NetContributed`, like a transfer in; a `Repayment` lowers the lender's `OutstandingPrincipal` and the source's `NetContributed`, like a transfer out. A borrow into a bucket leaves the currency's total unchanged; a borrow to the outside lowers it; a repayment from outside raises it. An `Adjustment` raises or lowers `NetContributed`.
- Income reports count `Deposit` only.
- Interest is **not** part of `OutstandingPrincipal` (see 4.4). This fixes an error in the earlier draft.

### 4.4 Loans

- **[P1]** `Loan`: lender bucket, principal, date, status. Created by `Borrow`. A loan can stay open with no schedule, or have a `RepaymentPlan` (monthly amount, versioned). A repayment cannot exceed the outstanding principal; the excess goes to remainder handling. A fully repaid loan gets status `Closed` and stays in history. Loans are allowed from savings buckets only.
- **As built in phase 1b:** a loan is an entity derived by replay from its `Borrow` and `Repayment` entries (its ID is the `Borrow`'s ID), never a stored document: principal, repaid, outstanding, status (`Open`, `Closed` when outstanding is zero) and the day it closed. A reversed repayment reopens the loan. The lender is a user's savings bucket (investment: `bucket.borrow_not_allowed`; `Unallocated`: `bucket.system_bucket`); destination and repayment source are in the lender's currency (cross-currency loans later) and differ from the lender (`borrow.same_bucket`, `repayment.from_lender`). A repayment above the outstanding principal, at any point of the replay order, is rejected (`loan.repayment_exceeds_outstanding`, parameter `date`); the allocation flow (4.7) handles an excess. The repayment plan is a list of `RepaymentPlanChanged` versions: expected repaid by the current month = min(principal, the monthly amounts since the first version); behind = expected − repaid. No pause or waiver of its own.
- **[P2]** Proportional repayment of all open loans of a bucket with one payment.
- **[Later] Interest on self-loans.** Design note for when it is built: interest is a separate entity (`LoanInterest`) that can be cancelled without touching the principal; accrued interest is tracked as `InterestDue`, separate from principal; paid interest is its own entry type that increases `NetContributed` and is reported separately from deposits; two methods (equal parts, on remaining balance); interest goes to the lender bucket.

### 4.5 Contribution plans [P1]

- `ContributionPlan`: bucket, monthly amount, `ValidFrom`, optional `ValidTo`, versions. Changing the amount creates a new version and never rewrites past periods. A bucket may have several plans.
- `DueByPlan` = sum of accrued periods from plan start to now − deposits linked to the plan. Computed, not entered. Payments settle the oldest period first.
- Shortfalls carry over (plan 500, paid 300 → next month 700 is due). This is an obligation to the plan, not a loan: it never changes `Available` and is never mixed with `Loan`.
- The end date stops new periods, not the obligation. A shortfall stays until it is paid or written off (`Waive`, with a reason).
- Overpaying a plan creates a prepayment that reduces future periods. One-time deposits without `PlanId` are outside this calculation.
- **Pauses (simplified)**: a pause exists only on a plan: `PlanPause { From, To?, Mode }`. `Shift` = paused periods do not accrue and the end date moves later. `Skip` = paused periods are dropped, the end date stays. The mode and dates can be changed later by a new event.
- **[P2] Bulk pause**: "pause all plans of a bucket" and "pause everything" are commands that create one `PlanPause` per plan with a shared `BatchId`. Any single plan can then be resumed on its own, including with a smaller amount (a new version). There are no scope-precedence rules.
- One-time deposits are never blocked by a pause.
- **As built in phase 1b:** a plan and its changes are journal entries (4.2). Periods are calendar months in the owner's time zone: an entry's month is the month of its `OccurredOn`; the current month is the month of today. A month accrues on its first day: the amount of the latest version starting at or before it, nothing when it is paused, and capped by the bucket's limit (4.6). Contributions are deposits and transfers in linked to the plan. Credit (contributions + waivers) settles the oldest accrued month first; `DueNow` = accrued through the current month − credit (never below zero); `Shortfall` = the part of `DueNow` from months before the current one; contributions beyond everything accrued are a prepayment for later months. A plan may start in the past (catching up) or later; not on `Unallocated`. `Shift` moves the end month by the paused months, `Skip` keeps it; pauses of one plan do not overlap. A waiver (`ShortfallWaived`, with a reason) may not exceed the shortfall at its date and never creates a prepayment. An **active plan** (it blocks archiving) is one that still accrues in the current month or later, or has `DueNow` above zero.
- **Past periods never change (invariant 6):** every definition entry (plan, pause, limit, repayment plan) and every reversal of one is checked by comparing each plan's accrual in every month before the current month without and with it; a difference is `plan.past_period_changed` (parameter `month`). A plan created by mistake with a past start is ended and its shortfall waived.

### 4.6 Bucket limit [P1]

- Savings buckets: the limit is compared with `NetContributed` (= available + outstanding principal), so a loan that will be returned does not free space.
- At the limit: plans stop accruing new periods and the UI shows that the goal is reached; payments can only repay loans. A deposit above the limit asks "raise the limit to X?"; confirming writes `LimitRaised`, declining cancels the deposit.
- **As built in phase 1b:** the limit applies to savings and investment buckets (4.9), always against `NetContributed`, and is replayed from `LimitChanged` entries (which replace `LimitRaised`: one type sets, raises, lowers and removes; not on `Unallocated`). A deposit, a transfer in or a borrow into a bucket that leaves `NetContributed` above the limit in force at its date is rejected (`bucket.limit_exceeded`, parameter `date`); opening balances, adjustments, reversals and repayments are not checked. A deposit or an allocation may carry the confirmed raise: the `LimitChanged` is written in the same commit with the same `GroupId`. A month of a plan accrues at most the room left on its first day (limit then − `NetContributed` at the end of the previous month), shared by the bucket's plans in the order they were created. Lowering a limit below `NetContributed` is allowed: the goal counts as reached.
- **[P2] Goal with a date**: limit + target date → required monthly amount and a forecast of when the goal is reached.

### 4.7 Payment allocation

- The engine is a pure function: input = amount, lines, plans, loans, rules; output = a proposed split and an unallocated remainder. Nothing is written until the user confirms. The split always sums exactly to the payment.
- **[P1] Manual mode**: the user gives explicit lines, each with a target (a plan, a loan, a one-time deposit into a bucket). The engine validates and caps each line (plan due, outstanding principal, bucket limit) and asks where the remainder goes: one-time deposit, loan repayment, plan prepayment, or `Unallocated`.
- **As built in phase 1b:** the payment comes from outside (it becomes deposits and repayments from outside) or from a bucket such as `Unallocated` (transfers and repayments from it). A read-only preview (`PreviewAllocation`) returns the capped lines, the reason for each cap and the remainder. The command (`AllocatePayment`) carries the confirmed lines with one ID each and one `GroupId`, and enforces only hard rules: the lines sum exactly to the payment (`allocation.sum_mismatch`), no target twice (`allocation.duplicate_line`), and every entry's own checks by replay; a plan line above the due is a prepayment and allowed. The caps are proposals, so what is written is exactly what the owner confirmed.
- **[P2] Automatic and semi-automatic modes**: buckets by numeric `Priority`; at equal priority debts first (plan shortfalls, then open loans, oldest first); if still undecided the system asks. `RemainderPolicy` per bucket or global (`Ask`, `ExtraDeposit`, `RepayLoan`, `Prepay`).

### 4.8 Accounts and reconciliation [P2]

- `Account` = where money physically is: bank account, cash, exchange, wallet, broker. It has a currency (or holds assets) and a user-entered or imported actual balance with a date.
- Buckets are virtual; accounts are real. Reconciliation compares, per currency, the sum of bucket balances with the sum of account balances and shows the difference. A difference is resolved with an `Adjustment` and a comment.
- This is the main protection against silent bookkeeping errors.

### 4.9 Investment buckets as seen by Budget [P1 model, P3 behaviour]

- An investment bucket has two independent numbers, both always shown:
  - **Invested**: `NetInvested` = deposited − withdrawn, in the bucket currency. It may become negative when more has been withdrawn than was put in.
  - **Current value**: `MarketValue`, provided by the Investments context at current prices.
  - `TotalPnL` = `MarketValue` − `NetInvested`.
- Plans and the limit of an investment bucket work on contributions (`NetInvested`), never on market value, so price moves do not block or unblock plans.
- Money leaves an investment bucket only through a withdrawal of portfolio cash (see 5.6). `Spend` and `Borrow` are not available on investment buckets. Until the Investments context exists (phase 3), money moves in and out of an investment bucket by `Transfer`, and the bucket shows `NetInvested` only. The "never negative" rule of 4.3 applies to savings buckets only.

## 5. Investments context [P3 crypto, P4 stocks/ETFs]

### 5.1 Structure

- Investment bucket → one `Portfolio` → `Section`s → holdings. Crypto default sections are configurable: **core** (5-6 coins with target shares), **active** (bots, open positions, unallocated stablecoins), **reserve** (stablecoins for adding to the core). The user can add, rename and remove sections.
- Everything held is an `Asset` with a quantity: coins, stablecoins, fiat cash, stocks, ETFs. A portfolio has a `ValuationCurrency` (USD for crypto).
- A system section **`Pending`** always exists and cannot be removed. A section cannot be closed while it holds anything; holdings are first moved elsewhere or to `Pending` (optionally marked "to sell"). Totals are computed from holdings, so rearranging sections can never change the portfolio total.
- A section is an **effective-dated assignment**. Moving a holding writes `Reclassify`; old entries are not rewritten, and a report "as of date X" shows the section of that date.
- `Location` of a holding = an `Account` (exchange, wallet, broker).

### 5.2 Portfolio journal

Separate journals for crypto and for stocks/ETFs, with shared base types. Append-only, same `Source` / `ExternalId` / two-date rules as Budget.

| Type | Meaning |
|---|---|
| `OpeningPosition` | Existing holding at start: quantity, cost basis, date. |
| `CashIn` | Contribution arriving from the Budget deposit (created by event). |
| `Trade` | Gives X of asset A, receives Y of asset B, plus fee. Covers buy, sell, crypto-to-crypto swap and fiat-to-stablecoin conversion. The UI may label them Buy / Sell / Swap. |
| `Income` | Staking, airdrop, bot payout, dividend (with withholding tax). Credited to a chosen section. |
| `Fee` | Standalone fee (withdrawal, network). |
| `Allocate` | Assigns cash or stablecoins to a section or container. |
| `Move` | Between locations (exchange → wallet). No change in quantity except the fee. |
| `Reclassify` | Changes the section of a holding from a date. |
| `CorporateAction` | Stock split, ticker change. [P4] |
| `CashOut` | Withdrawal of cash from the portfolio back to Budget or outside. |

### 5.3 Lots, positions, PnL

- Every acquisition creates a **lot** (quantity, unit cost, date, fee). Positions (quantity, average price, entry point, realized and unrealized PnL) are projections computed from lots. Storing lots keeps both average-cost and FIFO available later (for tax reports).
- Stablecoins allocated to a section count toward that section as unrealized (not yet deployed) capital.
- Prices come from `IPriceProvider` (first implementation: CoinGecko, free Demo plan with an API key; attribution to CoinGecko is shown in the UI), cached by a timer function and refreshed only as often as the free monthly quota allows. A paid plan can be added later without code changes. Stocks and ETFs [P4] use the same interface with end-of-day prices, which is enough because the broker holds the authoritative price and the app only needs a value for tracking. Free APIs cover European exchanges poorly (for example the free Twelve Data plan is US-only), so for a handful of ETFs any free end-of-day source is acceptable (the candidate to check first is Stooq daily data), and manual price entry always works as a fallback. The source is chosen in phase 4; a paid, reliable feed is added only if the app becomes a public service. Each price has a timestamp; stale prices are flagged in the UI; a manual price override is possible.

### 5.4 Containers for bots and futures

- Bots (spot, futures) and futures positions are not modelled trade by trade. A `Container` lives in a section and has: type, settings (free-form table), `AllocatedCapital` (stablecoins assigned by `Allocate`), manual `Valuation` entries (date, current value), payouts (`Income` credited to any section) and a close with a final result.
- Open spot positions in the active section are ordinary holdings created by `Trade`.

### 5.5 Strategy and targets

- `Target` per asset or section: core accumulation levels (price drops to a level → buy N% of reserve), profit taking in steps relative to the all-time high (exceeds ATH by X% → sell 5%), per-asset multiples (x2, x3, x4).
- Execution is manual. Each step has a status (pending, done, skipped) and is shown in a table; a price approaching a level is highlighted.
- **[Later]** Rebalancing hint: drift of core holdings from target shares and the trades that would restore them.

### 5.6 Getting money out

1. `Trade` asset → stablecoin or fiat (realized PnL is computed from lots).
2. `CashOut` from the portfolio. Budget records the matching movement out of the investment bucket: a `Transfer` into another bucket or a withdrawal outside. `NetInvested` decreases by the withdrawn amount.
3. Money arriving in a savings bucket this way is a transfer, not income. Profit is reported in investment reports.

Rule: a portfolio cannot withdraw more cash than it holds, and no holding quantity can go negative.

### 5.7 Value history [P3]

- The app stores **daily price history** per asset and daily FX rates (`PricePoint`), filled by a timer function. Portfolio value on any past date = holdings replayed from the journal to that date × the stored price of that date, so value history is always reproducible and survives corrections to old entries.
- Locally the app does not run every day: on start it back-fills missing days as far as the price and FX APIs allow (free plans limit how far back). Days that cannot be filled are shown as gaps, never invented.
- This feeds the charts and reports in section 13 and later performance metrics.

## 6. Integrations context [P5, groundwork in P1-P3]

- One connector per source behind `IImportConnector`:
  - crypto exchanges: read-only API keys (no trade or withdrawal permission);
  - wallets: public address, read through an explorer or node API;
  - brokers: API where one exists, otherwise the statement file the broker exports. XTB switched off its API on 14 March 2025, so XTB means file import.
- Pipeline: fetch → normalize into draft journal entries with `Source` and `ExternalId` → deduplicate on (`Source`, `ExternalId`) → show drafts → write on user confirmation. Per-connector auto-confirm may come later.
- Imported balances also feed reconciliation (4.8).
- Groundwork from the start: `Source` and `ExternalId` on all journal entries, the draft-and-confirm flow, the connector interface. No trading or withdrawals through any API, ever.

## 7. Invariants (each covered by automated tests)

1. `Available` of a savings bucket is never below zero.
2. `Available` = `NetContributed` − `OutstandingPrincipal` at any moment.
3. Journal entries are never modified or deleted; corrections are reversals.
4. A repayment never exceeds the outstanding principal, at any point of the replay order.
5. Income counts `Deposit` only.
6. Plan dues are derived from plan versions, pauses, limits, waivers and linked contributions; changing a plan, a pause, a limit or a repayment plan (or reversing such a change) never alters a period before the current month. Money entries may: a backdated deposit corrects what the bucket held.
7. Sum of sections (including `Pending`) = portfolio total; no holding quantity is negative; portfolio cash is never negative.
8. A bucket with a balance, an open loan or an active plan cannot be archived.
9. Allocation is deterministic and the split sums exactly to the payment.
10. State is always derived from the journal. When stored projections are introduced, each must equal a full replay.
11. `Money` of different currencies is never added without an explicit conversion.
12. Every query and write is scoped by `OwnerId`. Two documented exceptions (section 2.3): the outbox sweep, and reference data without an owner (FX rates, later prices) in `ref_` collections, which never hold owner data.
13. Handlers are idempotent for repeated commands and events (same `Id` → same outcome, no duplicates).

Testing approach: domain unit tests first; property-based tests for invariants 1, 2, 4, 6, 9 and 10, and a model test that runs random histories of every Budget command through the real handlers and checks invariants 1, 2, 4, 6, 9, 10, 11 and 13 (`BudgetModelTests`; 4, 6 and 9 from phase 1b); scenario tests built from real-life cases; integration tests against a real local MongoDB. Acceptance: run the app in parallel with the existing spreadsheet for two to three months and compare.

## 10. Decision log

| Decision | Reason |
|---|---|
| Serverless, one Function App with many small functions | Scales to zero, zero idle cost, one deployment and cold start, atomic in-process work. Contexts are isolated by project references, so a later split is cheap. A long-running host or a single giant function was rejected. |
| MongoDB locally and Atlas in the cloud | One engine and one adapter, real transactions, runs natively without Docker, no lock-in. Cosmos DB for MongoDB cannot do cross-collection transactions. |
| Journal is the truth; state is replayed, stored projections come later | History is never lost. Replay is simple and fast enough for one user; a cache is added only when needed, without changing handlers. |
| MongoDB only, no second relational database | Two stores would double the adapters and tests and cannot share a transaction. Reports are computed from replayed state or aggregation pipelines. |
| A first usable version (1a) before the full Budget core | The largest risk is never reaching real use; early use finds wrong assumptions cheaply. Nothing is dropped. |
| Store daily prices, not daily portfolio valuations | A stored valuation becomes wrong when an old entry is corrected; prices plus replay always give the right history. |
| Error codes in the API, text in the UI; strings in resource files | Keeps the contract stable and makes translation a later, code-free step. |
| Outbox instead of a queue | DB write and event publish must be atomic; a queue alone cannot guarantee it. |
| Repayment is its own entry type | Borrowing from yourself and returning must not inflate income. |
| Plan shortfall is not a loan | Different obligations; mixing them corrupts `Available`. |
| Pause only at plan level, bulk commands for wider scope | Same user experience, no precedence rules to get wrong. |
| Limit measured against contributions | A returnable loan does not free space; market moves do not affect plans. |
| One investment bucket = one portfolio | Limits, plans and pauses live on the bucket and stay unambiguous. |
| Invested and current value shown separately | Both matter for reporting; they are different numbers and must not be merged. |
| `Trade` as one two-legged entry | Buy, sell, swap and conversion are the same operation; fewer types, fewer bugs. |
| Bots and futures as containers | Margin, funding and bot internals do not fit buy/sell; capital + valuation is enough for tracking. |
| Lots are stored | Average price and FIFO both stay possible. |
| Imports create drafts | A wrong import must never write to the journal without the user. |
| Loan interest, auto-allocation, notifications deferred | Low value against complexity; the model leaves room for them. |
| `OwnerId`, no workspaces | Every user is individual. |
| Reporting currency is a switchable user setting | The owner earns in PLN, may hold EUR and tracks crypto in USD; totals are computed at read time, so switching costs nothing. |
| Frankfurter for FX, CoinGecko for crypto prices | Both free; both hidden behind interfaces so they can be replaced. |
| .NET 10 | Current LTS, supported by the Functions isolated worker until November 2028. |
| `Mediator` (source-generated, MIT) instead of MediatR | MediatR 13+ is dual-licensed (RPL-1.5 or commercial); it is free only below a revenue threshold and needs a registered licence key. The replacement has almost the same API, no licence risk, and no reflection at start-up, which shortens serverless cold starts. |
| Shouldly instead of FluentAssertions | FluentAssertions 8+ requires a paid licence for commercial use. |
| AGPL-3.0 for the project | Anyone may use and change it, but whoever runs a modified version as a service must publish the changes, so the code cannot be taken into a closed competing service. As the sole copyright holder the owner can still relicense later. Outside contributions are not accepted until a contributor agreement (CLA) is in place, to keep that option. |
| Permissive licences only for dependencies | The project may become a commercial service or open source; no dependency may block either. |
| Entra External ID by default, provider-neutral OIDC in code | One Azure account and a free tier; no provider SDK in the domain, so Auth0 or another provider is a configuration change. |
| AI agents as a separate read-only `Insights` context | The journal stays protected from model errors; agents reuse the read contracts; nothing in Budget or Investments has to change when AI is added. |
| One `ILedger` contract: read the version, then commit | Reading the version and committing against it are one protocol; the version is read before the journal so a concurrent write always causes a conflict, never a stale check. |
| Mutable documents are committed under the ledger version | Creating or archiving a bucket depends on the journal (no balance, no open loan), so it must be checked against the same version as journal writes; otherwise an archive and a deposit could race. |
| The handled-event record is part of the handler's commit | A handler's writes and the record that it handled the event are atomic, so a repeated delivery writes nothing (invariant 13). |
| Domain types are stored directly | One type per concept instead of a domain type plus a persistence type and mapping code; MongoDB mapping stays in Infrastructure, Domain stays free of database code. |
| Shared is split into `FinTrack.Shared.Kernel` and `FinTrack.Shared.Infrastructure` | Domain projects reference the kernel and must not reference MongoDB or the mediator library, so the adapter and pipeline code cannot live in the kernel. The name `Kernel` keeps the two projects apart. |
| Context projects are created in their own phase | Phase 0 creates Shared, Budget, Api and Web only. Empty Investments and Integrations projects would be dead weight until phases 3 and 5. |
| Two document shapes: mutable and append-only | `Version` and `UpdatedAt` have no meaning on a document that is never updated; append-only documents carry `RecordedAt` instead. |
| Each `Currency` carries its own decimal places | "Fiat has 2 decimals" is false for some currencies (JPY has 0). |
| The outbox sweep reads across owners | A timer has no owner; it must see every pending message. Each message is still handled under its own `OwnerId`. |
| HTTP functions use the ASP.NET Core integration of the isolated worker | Standard request and response types and simple `ProblemDetails`. The Functions host still owns the process, so this is not a long-running ASP.NET host. |
| CsCheck for property-based tests | Apache-2.0, written for C#, no F# runtime dependency. FsCheck was the alternative. |
| A split truncates each part; banker's rounding only for single values | Rounding each part to nearest and giving the remainder to the first line can make the first part negative for a positive amount (0.05 split 0.0001 : 1 : 1 : 1 would give −0.01, 0.02, 0.02, 0.02). Truncation keeps every part on the same side of zero and the sum exact. |
| The set of currencies is closed | Every currency is registered in code, so one code can never exist with two precisions. Tests define extra precisions through an internal factory. |
| Inter font is self-hosted under OFL-1.1 | The only accepted exception to the MIT/Apache/BSD rule, and for fonts only. OFL allows bundling and commercial use. Self-hosting keeps the app working offline. |
| MongoDB 8.0 is the minimum server version; CI tests 8.0, local servers may be newer | Atlas free clusters set the floor. A newer local server (9.0 on the first machine) cannot be downgraded easily once its data files are upgraded, and CI on the oldest version catches the use of newer features. |
| Instants are BSON dates in UTC with whole milliseconds; `IClock` returns whole milliseconds | A native date works with date queries and aggregations. A BSON date cannot hold finer ticks or an offset, so the clock never produces them and the serializer refuses them: in-memory state and state read back from the database are always equal, which keeps replay deterministic. An ISO string would keep 100 ns precision but lose date queries. |
| Reading stored documents is strict | A stored double, a number for an enum or an unknown element would otherwise be converted or ignored without notice; for financial data a loud failure is safer than a silent change. |
| Owner scoping and append-only are enforced by collection types | Contexts never touch a raw MongoDB collection: `AppendOnlyCollection<T>` has no update or delete method (rule 5), `MutableCollection<T>` replaces and deletes only with the expected `Version` in the write's own filter, and both add the `OwnerId` filter to every query and write (rule 9). A rule that cannot be called around is safer than one that must be remembered. |
| A duplicate document `Id` on insert is a `concurrency.conflict` | IDs are client-generated, so a second insert of the same `Id` means the same command ran twice or two writers raced; both are conflicts, never a second copy (invariant 13). Another owner's document behaves as if it did not exist, except that its `Id` cannot be reused. |
| Each context maps its document types to collections once (`LedgerDocuments`) | `LedgerCommit` carries documents, not collection names. A type (or its registered base type, so entry subtypes share the journal) maps to one collection named `<ledger>_...`; a document of another context's ledger makes the commit throw, which also enforces rule 3 at write time. |
| The handled-event record is written first in a commit; an outbox message's `Id` is its `EventId` | A repeated delivery is recognised before the version check, so it returns `AlreadyHandled` even when the handler read a version that has moved on; and one event can be stored in the outbox only once. |
| In-process dispatch through a decorating `DispatchingLedger`; each message in its own scope under its own owner | `MongoLedger` stays a pure write; the decorator delivers the committed events right after the commit and never fails the command. The sweep and the immediate dispatch use one code path: a new DI scope per message whose `ScopedOwnerContext` is the message's owner, so a handler can touch only that owner's data. |
| A failed delivery stays pending with `Attempts` and `LastErrorCode`; no retry limit yet | Handlers are idempotent, so retrying is safe; each failure is logged with its code. A dead-letter policy (a retry limit and a way to inspect stuck messages) is added when real handlers exist. |
| Validation failures: one `validation.failed` error per field, with `field` and `rule` only | The UI can mark each field and pick a text by rule; the value that was sent is never echoed back, because it may be an amount and error parameters may be logged. |
| A ledger command is retried at most 3 times in total on `concurrency.conflict`, without delay | Conflicts are rare for one user; three runs on fresh state are enough, and a bounded loop never hides a real problem. Other failures and exceptions are never retried. |
| `ErrorKind.Unavailable` (HTTP 503) for an unreachable dependency | A database or rate service that does not answer is neither a bug nor a business rule; the client may retry later. The health check reports an unreachable MongoDB this way instead of failing with 500. |
| Worker middleware: exceptions to `server.error`, the owner per HTTP request, indexes once per process | Cross-cutting work stays out of functions, which remain parse, send, map. Indexes are created before the first function that needs them; the health check is exempt so it can report a database that is down. |
| The light or dark choice is stored in the browser (`localStorage`) | It is a display preference of one device, not user data; without a stored choice the theme follows the system. A synced user setting can replace it when settings exist. |
| The Web project references Contracts and the kernel only when it first uses them | Phase 0 has no shared DTOs yet; the health answer is a small client-side record. Unused references would only add download size to the WebAssembly app. |
| The Api runs locally with `dotnet run`, not `func start` | Azure Functions Core Tools 4.16 warns that `func start` against a .NET isolated project may not load function extensions correctly and recommends `dotnet run`, which builds the project and starts the same host from the right output folder. |
| One branch and one pull request per plan step | `main` is protected and requires a green CI run, so every change is built and tested before it lands. |
| Journal entry types are Domain classes, mapped in Infrastructure with an explicit stable `type` name per subtype | One class per concept keeps each rule in one place. A stored type name that never derives from a CLR name survives refactoring, for the same reason as event names; a guard test requires one for every subtype. A flat document with nullable fields per type was rejected: every rule would become "if the type is X, field Y must be set". |
| Replay order is (`OccurredOn`, `RecordedAt`, `Id`); "never negative" holds at every point of it | Backdated entries are allowed, so a balance must be valid on every past day, not only today; otherwise bucket history and net worth over time would show impossible numbers. The order depends only on stored fields, so every replay agrees. |
| A reversal voids one entry as of its original date; reversals cannot be reversed | "Edit" = reversal plus a new entry must make history correct as of the original date; a compensating entry dated today would leave the past wrong. Not reversing reversals keeps every chain one level deep and easy to audit. |
| Repeated commands are recognised by the client-generated ID of what they create | The journal already records every handled command, so no extra collection or write is needed; a concurrent duplicate is caught by the unique `_id` and the conflict retry. |
| `Unallocated` is created in the same commit as the first entry that needs it | No separate setup call, and never an entry without its bucket; a concurrent first use conflicts on the ledger version and the retry finds the bucket. |
| A transfer stores both amounts as the truth and derives the rate | A typed rate and two typed amounts cannot be kept exactly consistent with rounding; a derived rate cannot be inconsistent. This refines "rate as entered by the user" (section 3). |
| Budget owns the owner settings (reporting currency, time zone, locale) | A document needs one owning context, and a separate settings context is not worth it yet; other contexts read the settings through `Budget.Contracts`. |
| Reference data (FX rates, later prices) has no `OwnerId` and lives in `ref_` collections | Rates are public and the same for every owner: storing them per owner would duplicate them, and a refresh has no owner to run under. A separate collection type keeps owner data out; it is the second documented exception to owner scoping. |
| `Contracts` holds read queries as mediator messages and may reference `Mediator.Abstractions` and `FluentResults` | Another context may reference only `Contracts`, and the read queries are the future agent tools, so the query types themselves must live there; commands and handlers stay in `Application`. Keeping only DTOs there was rejected: another context could not send the query. |
| Amounts travel in JSON as strings | A JSON number is read as a binary double by JavaScript and most tools and cannot hold 18 decimal places; the contract must not rely on both sides being .NET. |
| Investment buckets exist from phase 1a, without market value | Real use next to the spreadsheet needs the money that is already invested; deposits and transfers work now, spending is not allowed (4.9), market value arrives in phase 3. |
| Entries cannot be dated in the future | A balance "now" must not contain money that has not arrived; backdating stays allowed. |
| Amounts are strictly positive; one opening balance per bucket | The entry type gives the direction, so a sign on the amount would be a second, conflicting source of truth; a second opening balance would make the starting point ambiguous. |
| Budget storage and handlers are tested in their own integration test project | The stored format is permanent, so its tests belong next to the mapping they pin; end-to-end function tests stay in the Api test project. |
| Bucket names are unique among non-archived buckets, without regard to case | Two buckets that differ only in case cannot be told apart in lists and forms; an archived bucket frees its name. |
| The screenshot helper for UI checks lives in the repository (`scripts/dev`) | UI steps are checked by hand at 360 px and desktop width; a shared script (Node and a Chromium browser, no package) makes that repeatable. |
| Reading JSON over HTTP is strict, like reading stored documents | A double for an amount, a rounded decimal, a case-folded enum or an unknown property would otherwise be accepted and silently changed; the Api and the Web app ship together, so neither side needs tolerance. An instant has one spelling (`Z`) so equal values are equal text. |
| An unreadable request body is `validation.failed` with rule `JsonFormat`, not a new error code | Only a broken or hand-made client can send it (the Web app builds values with the kernel's checks first), so the UI needs no extra text; the field path still tells where. The value sent is never echoed. |
| Api JSON options go into MVC's `JsonOptions` | The Functions ASP.NET Core integration registers MVC and executes `IActionResult` through it, so MVC's output formatter writes every response; the minimal-API `JsonOptions` have no effect there (a test proves both). |
| Domain types are mapped by hand with explicit element names; the private constructor restores them | The stored format is permanent, so it must not follow C# names: a naming convention would change the format with a rename. Mapping the private constructor by reflection keeps Domain free of a public "restore" method and of attributes. Every element is required, so a missing one fails as loudly as an unknown one. |
| Time zone and locale are accepted only in their exact canonical form | The runtime's lookups also accept other spellings (any case, Windows time zone IDs on Windows, extra culture parts) and normalise them; storing what was typed would make two spellings of one value, and correcting it silently is a change without notice. |
| The settings document has a server-generated ID; saving unchanged settings writes nothing | One document per owner, created by the system on the first save, so the request needs no ID; comparing the values makes a repeated `PUT` harmless without an extra record (invariant 13). |
| `AddBudget()` in Budget.Infrastructure also registers Budget's Application services | Application may not reference the dependency-injection package (architecture guard); Infrastructure references Application anyway, so one call registers the context. Handlers are registered by the mediator's source generator in the host. |
| The Web app loads all ICU culture data | The owner's locale is a setting, not the browser's language. With the default shards (chosen by the browser's language; 144 to 249 KB compressed) an English browser has no data for `pl-PL`, so the app would format as English; measured in plan 1a step 4. All data is one file of about 330 KB compressed, at most about 190 KB more on a download of about 3 MB. |
| The owner's settings are loaded before the first render; a locale change restarts the Web app | Numbers and dates must be formatted by the owner's locale from the first screen. Setting the culture once at start is simpler and safer than re-rendering every component with a new culture. |
| Instants are shown in the owner's time zone | The owner's time zone decides "today" (section 3); showing times in the browser's zone would give two different clocks when they differ (for example when travelling). |
| Optional fields are absent when empty and read as empty when missing; everything else stays required | Keeps strict reading for the format while letting a later phase add a field (bucket `limit`, `Priority`) without an upcaster. Writing `null` would give two spellings of "empty". |
| Bucket names are compared ordinally without case, after NFC normalisation | The same result in every locale and on every server; a composed and a decomposed "é" are one name. Culture-aware comparison would make uniqueness depend on the owner's locale. |
| `Contracts` has its own copies of Domain's enums, mapped member by member | `Contracts` may not reference `Domain`. A test requires both copies to keep the same member names, which are the JSON and the stored names. |
| No route constraints; route and query values are parsed in the function | A constraint mismatch makes the host answer a bare 404 without a problem body; parsing gives `validation.failed` with the field, which the UI can explain. |
| The bucket list carries definitions only | Balances come from replaying the journal and belong to the overview (step 12); keeping them out keeps `GetBuckets` cheap and its V1 shape stable. |
| Entry types are sealed classes, not records (refines D1) | A record adds a copy constructor and `with`, a second way to build an entry that bypasses the factory's rules, and its generated equality compares the tags list by reference; the repeat check is an explicit `HasSameContent` instead. |
| The replay order compares IDs by their big-endian bytes | That is MongoDB's order for stored UUIDs, so the order in memory and a sort or range read in the database are the same; written out instead of relying on `Guid.CompareTo`, which happens to agree. |
| A repeated command is recognised before the rules are checked | It was valid when it was written; a later change (an archived bucket, the date moving past today's limit in another time zone) must not turn a harmless repeat into an error. |
| The target of a deposit is a bucket ID or "Unallocated of a currency" | `Unallocated` has a server-generated ID the client may not know yet; naming it by currency lets the first deposit create it in the same commit (D5). |
| Invariant 1 is checked by replaying the journal with the new entry | One rule for every entry type, also backdated ones and (step 9) reversals; the state builder records the first day each bucket went below zero, so the error can name it. Replaying the whole journal per command is fast for one owner; a stored projection can replace it later without touching the rule. |
| Single-bucket entries share one write path | Opening balance, deposit and spend differ only in direction and one rule each (one opening balance; no spend from an investment bucket); one path keeps target resolution, repeats and the never-negative check identical for all three. |
| The state loader reads the version before and after the documents | Settings, buckets and journal are separate reads; a commit between them gave a state whose journal referred to a bucket missing from its list (found by CI in step 7, when every command began to replay). Every commit raises the version in its own transaction, so an unchanged version proves a consistent read. A MongoDB snapshot session was the alternative; it would have needed the version read inside the same session, which the kernel's `ILedger` does not offer. |
| A transfer's own rules are 400, the rate has 12 decimal places | Same bucket, a fee not below the amount, and inconsistent same-currency amounts can be seen in the request alone, like other malformed input; checks against stored state (insufficient funds, archived, currency of the bucket) stay 422. Twelve places show any realistic rate, also between currencies of very different value, without the noise of a full 28-digit quotient; the amounts remain the truth. |
| One write path for every entry type (`JournalWriter`) | Transfers need two targets and two bucket checks; generalising the step-7 path keeps the order of checks (repeat first, then rules, then invariant 1 by replay) identical for every type, and lets both sides of a transfer share one `Unallocated` created on demand. |
| A reversal of an entry that touches an archived bucket is rejected | An archived bucket accepts no change to its balance; reversing a spend would put money back into it. Not in D3 as written; added in step 9. |
| Reversals are resolved before the replay | The state builder leaves out reversed entries and the reversals themselves, so the replay order is unchanged and a reversed entry counts as if it never happened at its original date; the step-by-step build runs over the same effective journal. |
| The model test runs the real handlers against an in-memory ledger and store | Thousands of random histories per run need memory speed; the in-memory budget behaves like the MongoDB adapter where handlers can tell (expected version, unique IDs, version stamping, replay order), and MongoDB itself is covered by the integration tests. A coverage check requires every command to be both accepted and rejected somewhere, so the invariants are not checked against trivial histories. |
| "Fetched today" for FX rates is the UTC day of the most recent fetch | Rates are reference data without an owner, so no owner's time zone can apply. Judging by the fetch time, not the rate date, keeps a weekend or early-morning answer (an earlier rate date) from being re-requested on every page load; the price is that the day's new rates published around 16:00 CET are picked up the next UTC day at the latest. |
| No integration events in phase 1a | Nothing consumes them before the Investments context (phase 3); events without a consumer would be dead code. The outbox stays ready. |
| The reporting total is all or nothing; it carries the oldest rate date | A total that silently leaves out a currency whose rate is missing would look complete and be wrong, so one missing rate leaves the converted total out with its reason (`fx.rate_unavailable`) while the per-currency totals stay. Rates of different currencies can have different dates (offline fallback); showing the oldest never presents the total as fresher than it is. Each currency's total carries its own rate and date. |
| Overview totals cover active buckets only, investment buckets at their net invested amount | Archived buckets always hold zero (invariant 8), and counting them would add empty currencies to the totals. Investment buckets are part of what the owner has; until market value exists (phase 3) their figure is the net invested amount, which may be below zero. |
| The journal DTO is one flat shape with a `type` | A read DTO, not the domain model (D1 rejected a flat model for the domain and storage): one shape is simpler for JavaScript and future agent tools than polymorphic JSON, which strict reading would also have to support; fields of other types are `null` and documented per type. |
| The journal cursor is the replay position of the last entry, opaque to clients | A position (date, recorded time, ID) lets a later database-side read continue with a range read on the `replay_order` index without looking the entry up; entries are only added, so paging never repeats or skips an entry. Encoded as versioned Base64url with one spelling; its content is not part of the contract. An entry-ID cursor was rejected: it needs a lookup first. |
| Money is shown with its ISO code, placed as the locale places its currency symbol, the sign always first | A symbol can leave the currency unclear (`$` is shared, a locale's own symbol is its own currency's), which DESIGN 6 forbids. Following the locale for placement keeps amounts familiar; one rule for the sign is easier to read in a column. The minus is U+2212. |
| Typed amounts are read strictly in the owner's locale and never rounded | A misread amount is worse than a rejected one: `12.50` in `de-DE`, where the dot groups thousands, is rejected rather than read as 1250. Too many decimals is the kernel's `money.too_many_decimals`, the same check as the Api; the value sent has the currency's scale, so the Api receives one spelling. Client-side codes `input.amount_required` and `input.amount_invalid` (with an `example` in the owner's locale, never the text typed). |
| Error texts with parameters use an optional `Error.<code>.WithParams` template | The plain text always exists (the known-codes test); a template is used only when every placeholder has a parameter, so a missing parameter never shows a raw `{date}`. Parameters are shown in the owner's locale (a business date as its short date); texts stay in resource files, never concatenated. |
| Buckets are created and renamed in dialogs over the list; the list has no balances | Both are short edits that return to the list, so a dialog keeps the owner in place (full width on small screens). The list stays on `GetBuckets` (definitions only): balances need the overview, which may wait for the rate service, and they belong on the Overview. Archiving a bucket that still holds money is explained from `bucket.not_empty`. |
| The Overview shows only the Api's figures; the currency list only with a second currency; bucket colours wait for the charts | Nothing is computed in the Web app, so the page and the read contract can never disagree. With one currency the per-currency list would repeat the total. DESIGN 4's colours mean "the same bucket in every chart"; assigning them now, before any chart, would fix an order the charts of phase 2 may need to choose differently. |
| Entries are added on one page with a summary step, and the form stays open after saving | Several fields and a confirmation read better as a page than as a dialog, also on a phone; staying on the form with a fresh ID (kind, date and buckets kept) makes catching up from the spreadsheet quick, and a snackbar leads back to the Overview. One ID per form makes a double click or a retry write once; the button is also disabled while a write runs. |
| The Web app checks entries with the server's rules and codes before sending | The owner sees why before confirming (DESIGN 9). Where the server has a code (`entry.date_in_future`, `transfer.same_bucket`, `transfer.fee_exceeds_amount`, `money.amount_not_positive`, `money.too_many_decimals`) the form uses it, so one text explains both; checks with no server code get `input.*` codes. The server still decides. A rate typed by the owner only computes the amount received, rounded once with banker's rounding; that amount is sent, and the server derives the stored rate (D6). |
| The Journal pages with "Load more" (25 entries) and names a reversal's target only when it is loaded | The cursor already gives every entry once (step 12), and appending keeps the owner's place in a long list. Newest first, a reversal is usually above the entry it cancels, which may be on a later page; the row then says "Cancels an earlier entry", and the reversed entry carries the "Reversed" label wherever it appears. A query for one entry is not worth adding in phase 1a. Reversal is offered only where the server would accept it in principle (not a reversal, not reversed, no archived bucket); the server still checks invariant 1 and explains a refusal. |
| Tests are checked by mutation: by hand in every step, and with Stryker.NET on the kernel, Domain, Application and the Infrastructure projects | A test is only as good as the bugs it notices. Every plan step breaks its own code on purpose and requires the tests to fail; Stryker.NET (a local tool, Apache-2.0) does the same systematically for the pure layers, where the money rules live. Survivors are classified as missing tests or as equivalent changes, never ignored silently. The configuration (`stryker-config.json`) skips argument guards, `ConfigureAwait` and exception messages, which only describe programming errors. Stryker 5.1 cannot compile the Blazor WebAssembly project (it does not run the Razor source generators), so the Web app's plain classes stay covered by the per-step mutations; the Api is thin and covered by its integration tests and per-step mutations. Infrastructure runs against MongoDB; its setup that runs once per process (class maps, serializers, static options) cannot be switched by Stryker and is checked by hand (`docs/plans/test-audit.md`). |
| Plan, pause, limit and repayment-plan definitions are journal entries (plan 1b B1) | Append-only by construction, one state builder over buckets and journal, every change dated and visible, corrections by reversal, bulk pause later as entries sharing a `GroupId`. A plan's months depend on the limit of their own time, so the limit needs a history; a single stored field would revive months in which the bucket was full. Mutable documents with version lists were rejected: their history would be protected only by the code that appends to it. |
| A loan is derived by replay from its `Borrow` and `Repayment` entries (B2) | A stored loan with a status would be a second truth that every repayment, reversal and backdated entry must keep in step. Same currency only in 1b: a cross-currency loan would need two amounts and a rate like a transfer. |
| Borrowing lowers the lender's `Available` through `OutstandingPrincipal`, not `NetContributed` (B3) | A returnable loan must not free space under the limit and a repayment must not be income; the destination receives the money like a transfer in, so a borrow between buckets leaves the total unchanged. |
| A single repayment above the outstanding principal is rejected (B4) | It has no remainder to handle; splitting the excess silently would write an entry the owner did not confirm. The allocation flow caps the loan line and asks where the rest goes. |
| An entry that effective entries refer to cannot be reversed (`entry.has_dependents`, B5) | A repayment of a reversed loan or a contribution to a reversed plan has no meaning; the replay check would catch most cases, but with a code that names the symptom instead of the cause. |
| Months are a kernel `YearMonth`, `yyyy-MM` in BSON and JSON (B6) | Periods are months; a `DateOnly` that must be the 1st would be a second spelling of every month and a rule every reader must remember. |
| A plan month accrues on its first day; credit settles the oldest month first; a prepayment settles later months (B7) | Matches 4.5's carry-over example (500, paid 300, then 700 due) and keeps the current month separate from the shortfall that needs attention. |
| Invariant 6 is checked generically: past months without and with the change (B8) | One check, property-tested once, covers versions, pauses, end months, limits and their reversals; a rule per kind of change could miss a case. Money entries are exempt because they correct what the bucket held. |
| Transfers can be linked to a plan as well as deposits (B9) | The owner's usual flow is salary into `Unallocated`, then distribution by transfer; with deposits only, money already in `Unallocated` could never pay a plan. A linked transfer is still not income. |
| Pauses are entries; `Shift` moves the end, `Skip` keeps it; no overlap (B10) | 4.5's "changed later by a new event"; the latest change of a pause wins and the earlier ones stay in the journal. |
| A waiver needs a reason, may not exceed the shortfall at its date, and never creates a prepayment (B11) | Writing off an obligation must not turn into credit when a later backdated contribution covers the same months. |
| `LimitChanged` replaces `LimitRaised`; deposits, transfers in and borrows into a bucket are checked; a plan month accrues at most the room left (B12) | One type for set, raise, lower and remove. Opening balances, adjustments and reversals record facts and are not checked; repayments never raise `NetContributed`. Capping each month keeps a plan from asking for money the limit would refuse. |
| A repayment plan has versions only; expected = min(principal, monthly amounts so far) (B13) | The principal is the obligation; the plan only says how fast. Pauses and waivers would add rules without a real need. |
| `Adjustment` is one type with a `direction`; the comment is the required note (B14) | Amounts stay positive (D13); one type keeps one set of rules; tracked separately in the state for the phase-2 reports. |
| A command may write several entries, each with its own client ID, sharing a client-generated `GroupId` (B15) | IDs derived from one group ID would be a second kind of ID beside UUIDv7; a repeat is recognised over the whole group. |
| Allocation: a read-only preview, then a command with the confirmed lines that enforces only hard rules (B16) | What is written is exactly the summary the owner confirmed; re-running the engine at commit time could write something else. The Web app shows the Api's preview and computes nothing. |
| Archiving has three codes: open loan, active plan, not empty (B17) | The UI must say which cause blocks and what to do next; `Available` alone misses a lender whose money is all lent out. |
| `V1` grows additively until its first consumer that does not ship with the Api (B18) | The Web reads strictly but ships with the Api; agents and other contexts use the query types in-process. The flat journal DTO gains fields per type (polymorphic JSON stays rejected). |
| Plans, loans and "needs attention" are read queries; the overview gives figures, not percentages (B19) | They are the future agent tools; a progress bar is display, computed from `limit` and `netContributed`. |
| The state builder takes today (B20) | Dues need the current month; Domain stays pure because today is a parameter computed in Application. Replay speed is measured in plan 1b step 18 before any projection is considered. |
| Phase 1b screens reuse the 1a patterns (B21) | Form models in plain C#, one client ID per form, the server's codes checked first, a summary before writing; Plans and Loans join the navigation with their pages. |
| No new package in phase 1b (B22) | Everything is built on what is there; MudBlazor stays on 9.13.0 and the Microsoft packages on the .NET 10 line. |
| An archived bucket can be unarchived (B23) | An archived bucket is empty, lends to no open loan, has no active plan and received nothing while archived, so making it active again changes no replayed figure. One purpose keeps one bucket and one history; a new bucket would split it. Only the name can conflict (archiving frees it), which `bucket.name_taken` reports. Archiving automatically when a bucket empties was rejected: an empty bucket with a plan still expects contributions. |
| Every `Money` amount has exactly its currency's decimal places (plan 1b step 2b) | Found in step 2: an empty bucket and the always-zero `outstandingPrincipal` answered `"0"` while other amounts answered `"50.00"`, because zero and amounts sent with fewer decimals kept the scale they were created with. Contracts, agent tools and stored values should see one spelling per amount. Normalised once in `Money` (every value passes its constructor) instead of in each serializer; equality and comparison already ignored scale, so no rule changes. Rates and other plain decimals keep their exact scale. Alternative: only `Money.Zero` at the currency's scale; rejected because an amount sent as `"50"` would still come back as `"50"`. Consequence for phase 3: a currency with 18 places prints all 18. |
| A repeat of a grouped command matches the stored group exactly (plan 1b step 3, refining B15) | B15 compares the command's entries with the stored ones; read literally, it would accept a command that repeats only part of a stored group, and new entries sent under a group ID that is already stored. Both break "a group is the entries of one user action", so both are `entry.id_reused`, like any other difference. The writer recognises a repeat when any entry ID or the group ID is stored. Archiving now needs the owner's settings (`settings.not_found` before the first run), because the state it checks is built for today (B20); no screen can archive before setup. |

## 11. Setup choices and open questions

Resolved:

- Name: **FinTrack**, an internal working name and namespace prefix (`FinTrack`). It is deliberately plain and not meant as a product name; a public name is chosen only if the app is ever released, and renaming is a find-and-replace.
- Runtime: .NET 10 (LTS).
- Reporting currency: a user setting, switchable at any time. Crypto is valued in USD.
- FX rates: Frankfurter API. Crypto prices: CoinGecko Demo plan. Stock and ETF prices: end-of-day, free source behind `IPriceProvider`, manual entry as fallback.
- Cloud identity: Microsoft Entra External ID by default, provider-neutral OIDC in code.
- Libraries: `Mediator` (Martin Othamar, MIT, source-generated) instead of MediatR; FluentResults; FluentValidation; MudBlazor; xUnit; Shouldly instead of FluentAssertions; CsCheck for property-based tests; `Microsoft.Extensions.Http` for calls to external rate and price services. ## 12. Insights and AI agents [Phase 7, design constraints apply now]

Nothing in this section is built in phases 0 to 6. It is recorded so that earlier phases do not block it.

### 12.1 What it is for

- **Explain my portfolio**: why the value changed, what moved, how the plan is going, what a number means.
- **Ask questions** about own data in plain language.
- **Research**: an asset or project (fundamentals, news, market context), macro context, a trading setup.
- **Suggestions**: options for a situation, always as information for the user to decide on.

Concrete features are specified when the phase starts.

### 12.2 Architecture

- A separate bounded context, **`Insights`**. It may read other contexts only through their read contracts (2.6). It has no access to their collections.
- **Agents never write to the journal.** The most an agent can do is create a draft or a proposal (for example a suggested target level or a suggested allocation), which the user confirms through the normal draft-and-confirm flow. Such drafts carry `Source = Agent:<name>`.
- An agent = a model + a set of **tools**. Tool groups: portfolio tools (the read contracts), market tools (`IPriceProvider`, `IFxRateProvider`, value history), research tools (web search and page reading, added in that phase). All tools are read-only.
- The model sits behind an interface (`ILlmClient`), so the provider can be changed and a local model can be used in offline mode.
- **Runs are asynchronous.** An HTTP function creates an `AgentRun` document (status, steps, tool calls, result, token usage, cost) and returns at once; a queue-triggered function executes the run step by step and saves progress after each step; the UI polls or streams the status. A run can be cancelled and resumed.
- Research results can be saved as `ResearchNote`s linked to an asset, with their sources and date.

### 12.3 Rules

- **Cost**: model calls are paid per token and are the only part of the system that is not free. Agents run only on a user's request, never in the background by default. Each user supplies their own API key (required for local and open-source use). Every run records its cost, and a per-user spending limit stops runs when reached.
- **Privacy**: sending data to an external model is opt-in. Send the minimum needed; an option replaces absolute amounts with percentages. API keys are stored like other secrets (2.8).
- **Trust**: answers show which data and sources they used. Output is information, not financial advice, and is labelled so. Text fetched from the web is untrusted data and is never treated as instructions; because every tool is read-only, a manipulated page cannot change the user's records.
- **No trading**: agents cannot place orders or move money. This follows from section 6 and does not change.

### 12.4 What earlier phases must provide

- Read contracts with stable DTOs (2.6), from phase 1.
- Value history (5.7) and realized/unrealized PnL per position (5.3): needed to explain changes.
- Targets, notes and tags on entries: the context an agent needs to understand intent.
- The draft-and-confirm flow as a shared mechanism (4.7, 6), with `Source` on every entry.
- Asynchronous job pattern (`AgentRun`-style document + queue) introduced no later than phase 5 for imports, then reused.

## 13. Analytics and reports

A finance tool must show where things stand and how they move. Everything here is read-only and computed from the journal plus stored price and FX history; nothing is entered twice. Each chart has a table with the same numbers, and every report can be exported to CSV. Queries live in the read contracts (2.6), so the same data later serves the AI agents.

### 13.1 Budget

| Phase | Item |
|---|---|
| 1a | Overview: total per currency and in the reporting currency; a card per bucket with available amount. |
| 1b | Bucket cards add progress to limit, due by plan, shortfall and open loans. "Needs attention" list. |
| 2 | **Net worth over time**: all buckets in the reporting currency, monthly points (computed by replay at each month end, with that date's FX rate). |
| 2 | **Plan versus actual**: planned and actual contributions per month, per bucket and in total. |
| 2 | **Allocation**: share of each bucket in the total. |
| 2 | **Bucket history**: balance of one bucket over time with its deposits, spends and loans. |
| 2 | **Monthly report**: deposits, spends, transfers, shortfalls carried over, loans opened and repaid, change in net worth. |

### 13.2 Investments

| Phase | Item |
|---|---|
| 3 | **Portfolio value over time** against **net invested** on the same chart, so growth from the market is visibly separate from growth from contributions. Period selector (1M, 3M, 1Y, all). Deposits and withdrawals are marked on the line. |
| 3 | **Allocation** by section and by asset, compared with target shares. |
| 3 | **Positions table**: quantity, average price, current price, value, unrealized and realized PnL in amount and percent. |
| 3 | **Targets table**: next levels and distance from the current price. |
| 4 | The same for stocks and ETFs, plus dividends received per period. |

### 13.3 Later

Time-weighted return and XIRR; comparison with a benchmark; drawdown; yearly summary; tax report. These reuse the stored price history and lots, so no model change is needed.

### 13.4 Rules

- A converted figure always shows its currency and the rate date.
- A chart never draws a value for a day without a price; it shows a gap.
- Reports are generated on request. There is no scheduled report sending in the first phases (notifications are out of scope).
